## 1. 概述

当前可交流模式能让 LLM 复述 KataGo 的胜率/目数/候选点，但深层次问题（「为什么下这里不好」「为什么做不活」）统一答「不知道」——因为 Grounding 数据里没有「原因」。本设计从三条线补齐：

1. **讲解增强**：把「为什么」用确定性逻辑从 KataGo 数据里预先抽出，LLM 只翻译不推理。
2. **棋盘演示**：AI 在棋盘上逐步演示变化图（固定前几步 + 权威 AI 后续等模式），边下边讲、逐步确认。
3. **Skills 配套**：用围棋领域知识包弥补通用 LLM 的专业度不足。

---

## 2. 现状与问题

| 现象 | 根因 |
|---|---|
| 「为什么这步不好」答「不知道」 | 用户问的那一点不在前 4 候选里，LLM 手里没有该点的胜率/目数对比 |
| 「为什么做不活」答「不知道」 | ownership（死棋信息）没进 prompt，也没有死活结论 |
| 讲解只有文字，新手难理解 | 没有棋盘演示，看不到「几步之后会怎样」 |
| 边下边讲做不到 | LLM 非流式（M4.1 待做） |
| 通用 LLM 围棋专业度不足 | 没有领域知识注入 |

---

## 3. 总体架构

```
用户提问
  → 问题分类（新增：落点质量 / 死活）
  → 分析层（KataGo）：what-if 落点评估 / 死活判定 / ownership
  → 事实抽取（确定性，无 LLM）：delta、死活结论、死棋清单
  → Skills 注入（按问题类型选知识包）
  → LLM 生成自然语言（诚实条款约束）
  → 可选棋盘演示（变化图 + 逐步 + 流式，由用户确认推进）
```

新增/改造组件：

```
src/ai/
  evaluate.*         MoveEvaluator（what-if 落点评估）
  lifedeath.*        LifeDeathAnalyzer（死活判定，确定性启发式）
  skill.*            Skill / SkillRegistry（围棋知识包）
  variation.*        Variation（变化图数据 + 逐步推进状态机，无 Qt）
src/ai/conversation_http/   SSE 流式（M4.1 落地）
src/ui/
  VariationPanel.*   演示面板（棋盘演示态 + prev/next/确认控件）
  GobanWidget         支持演示态渲染（变化图手数/编号）
```

## 4. 讲解增强（N1）

### 4.1 问题分类细化

把笼统的 `WhyThisMove` 拆成三类，分别走不同分析：

| QuestionClass | 触发词例 | 分析 |
|---|---|---|
| WhyThisMove | 为什么下这里（无落点） | 最近一手结构事实（现有） |
| MoveQuality | 为什么下这里不好 / 这步行吗 / X 点如何 | what-if 落点评估 |
| LifeDeath | 为什么做不活 / 这块棋死没死 / 能活吗 | 死活判定 |

### 4.2 落点质量评估（what-if）

- 新增 `MoveEvaluator`：`evaluate(game, point, cb)`。
- 流程：把 `point` 下到棋盘**副本** → 再 `kata-search_analyze` → 与原局面对比。
- 产出事实（喂给 LLM）：

> 「下 G3 后黑方胜率 55%→40%，领先 +2→-1（亏约 3 目）；当前更该下 F4（胜率 55%）。」

### 4.3 死活判定

- 用 ownership 识别死棋（复用 `deadStones`）。
- **防守搜索**：对该块，把防守方候选点逐一下到副本看 ownership 是否翻正；全部翻不正 → 「没有任何一手能救活」。
- 产出事实：

> 「左下这块黑棋被判死——试遍候选点都无法做出两只眼，所以做不活；对方围住即可。」

> 更细的「眼位太小 / 要点被占」属于死活题求解，见 §4.5。

### 4.4 丰富 GroundedFacts

`GroundedFacts` 增加：死棋清单、落点 delta、死活结论；`buildUserPrompt` 一并渲染。

### 4.5 眼形/要点分析（长期 N6）

局部几何死活题求解（算眼位、找 vital point），或接入围棋专用模型辅助。高难度，后置。

## 5. 棋盘演示（N2）

### 5.1 变化图（Variation）

演示不修改真实对局，用独立的 `Variation`：

```cpp
struct VariationStep {
    Move move;             // 这一手
    Color color;           // 谁下
    std::string explanation;  // 讲解文本（可流式累积）
    std::vector<Point> marks; // 要圈出的要点/死棋
};
struct Variation {
    Board start;           // 起点 = 当前局面副本
    Color to_move;
    std::vector<VariationStep> steps;
    int cursor = 0;        // 当前演示到第几步
};
```

### 5.2 演示模式（按用户要求）

| 模式 | 说明 |
|---|---|
| 固定前几步 | 用户指定前 N 手（如「先下 A、B、C」），后续交 AI |
| 权威 AI 后续 | 复用形势判断引擎（与形势分析同一引擎、同一强度档位） |
| 自由逐步 | 每步由用户或 AI 落子，自由试下 + 回退 |
| 提问触发 | 用户问「如果白棋在H6…黑棋后面几步该如何应对」等，AI 落假设手并权威 AI 连续续下；LLM 经 function-calling（工具 `demonstrate_go_moves`）自行决定何时/如何演示，无 LLM 时用关键词 `parseDemoRequest` 兜底 |
| 继续/重置/回退 | 工具带 `reset`（true=从头）、`undo_to`（回退到第 k 手之前，用于「重新假设第 k 手」）、`point/color/plies` 参数；演示上下文按手数编号喂给 LLM。工具同步跑完权威 AI 续下、取得具体坐标后才回传 LLM，避免「没有具体坐标」；有 LLM 时演示请求一律走工具（演示后还能讲解），无 LLM 才用关键词 `parseDemoRequest` 兜底 |

实现：`Variation` 记录「每步由谁落子」；AI 步调用分析引擎，用户步由点击棋盘填充。

### 5.3 试下模式（实现变更，替代「逐步确认」）

> 实际实现改为「试下模式」：无需每步讲解、无需「确认下一步」。变化图可自由试下/回退，
> `VariationController` 无 Qt、可单测；`back()` 直接弹出最后一步，因此回退后可见的最后一手
> 恒为当前局面实际下过的一手（修复讲解 off-by-one）。聊天问答与形势判断均针对当前变化图局面。

```
试下 →（AI/用户）落子 → 自由试下 → 回退 / 退出
```

### 5.4 UI

- 进入试下态：棋盘切到变化图，叠加「AI 演示一手」「回退」「退出演示」控件。
- 变化图手数以编号标在棋盘上（区别于真实对局）。
- 退出后恢复真实对局棋盘。

## 6. 同步流式（N3）

- **落子与讲解同步**：每步先落子（KataGo，快），讲解（LLM）随 SSE 流式追加到聊天面板。
- 依赖 M4.1 的 LLM 流式：`HttpConversationService` 支持 `stream=true`，逐 token 回调。
- 「下棋 AI」与「讲解 AI」解耦：落子走 `analysis_engine_`（满血），讲解走 `conversation_`（LLM），同一变化图逐步推进。

## 7. Skills 系统（N4）

### 7.1 概念

`Skill` = 一段可注入的围棋领域知识（system prompt 片段 + 术语 + 少量示例），弥补通用 LLM 对围棋专业度不足。

```cpp
struct Skill {
    std::string id;                 // "life-death"
    std::string name;               // "死活基础"
    std::vector<QuestionClass> applies_to;  // 命中的问题类型
    std::string prompt;             // 注入的知识正文
};
class SkillRegistry {
    // 按 QuestionClass 挑选匹配的 skill，拼进 system prompt。
    std::vector<const Skill*> forQuestion(QuestionClass q) const;
};
```

### 7.2 内置 Skills（首版）

| id | 内容 | 命中 |
|---|---|---|
| life-death | 两眼活/一眼死、真眼假眼、眼位大小 | LifeDeath |
| move-quality | 落子对比怎么看胜率/目数变化 | MoveQuality |
| counting | 数子法、领地、死子、贴目 | WhoIsWinning |
| ko | 打劫规则、找劫材 | Other |
| terms | 术语：打吃、提子、连接、延展、扳、断 | 全部 |

### 7.3 存储与热更

- Skills 以 markdown/JSON 数据文件存放（`resources/skills/*.md`），启动时加载。
- 可增删改、不重编译；后续可扩展成带示例的 few-shot。

## 9. 任务计划

| 阶段 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| N1 | 讲解增强：分类细化 + what-if + 死活 + GroundedFacts 扩展 + prompt | `evaluate.*` `lifedeath.*` + 单测 | 无 |
| N2 | 棋盘演示：Variation + 模式 + 逐步状态机 + 演示态 UI | `variation.*` `VariationPanel.*` | N1 |
| N3 | 同步流式：LLM SSE + 逐步确认串联 | `conversation_http` 流式 | N2 |
| N4 | Skills 系统：知识包 + 注入 | `skill.*` + 内置 skills | N1 |
| N5 | 打磨：全量测试 + 打包 + 术语语料迭代 | 测试/文档 | 全部 |
| N6 | 眼形/要点分析（死活题求解） | `lifedeath.*` 深化 | 长期 |

**关键路径**：`N1 → N2 → N3`；`N4` 可与 N1 并行；`N5` 收尾；`N6` 长期。

## 10. 验收标准

- 「为什么下这里不好」能给出含胜率/目数变化的量化答案，而非「不知道」。
- 「为什么做不活」能指出哪块棋、并给出「无救活之手」的诚实结论。
- 试下模式：用户可指定「固定前几步 + 权威 AI 后续」，自由试下、可回退、可退出，不影响真实对局。
- 讲解随落子流式呈现；LLM 未接时回退模板文本。
- 对应问题自动加载匹配的 Skill，知识可热更。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 死活/眼形分析难 | 先用 ownership+防守搜索给「能/不能活」的诚实结论，眼位/要点后置（N6） |
| 演示与真实对局混淆 | 变化图独立数据 + 棋盘编号 + 明确「演示态」标识 |
| 流式顺序错乱 | 落子先行、讲解流式追加，逐步由用户确认推进 |
| LLM 仍幻觉 | 保留 Grounding 诚实条款，delta/死活结论作为硬事实 |
