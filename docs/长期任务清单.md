#### L10 — 持续优化 LLM 模型的 Skills 🔁（P0，本次新增）
- **进展（D4）**：Skills 2.0 已落地——`Skill` 升级为 YAML frontmatter（id/name/description/applies_to/version/last_score）+ body；新增 TF-IDF 语义检索（`SkillRegistry::retrieve` 带命中理由，embedding 为后续前端）；`HttpConversationService` 经 `SkillRegistry::select`（类别白名单 + 检索 top-k、按 id 去重、受预算裁剪）注入。**D4.5 评估闭环已落地**：`skill_eval.*` 定义 golden Q&A 集 + `SkillEvalReport`（分类命中率 / Top-1 检索命中率 / 每技能评分 / 注入数 token 代理），纳入 CTest 作 release gate（`test_skill_eval`，命中率 ≥ 90% 才通过）。`version` + `last_score` 使 L10 从此有度量与完成标准。
- **背景**：通用 LLM 对围棋专业度不足，项目用 `resources/skills/*.md`（counting / ko / life-death / move-quality / terms 五个知识包）按问题类型注入 system prompt。这些知识包的质量直接决定 LLM 讲解的专业度与可信度。
- **为什么是长期任务**：围棋领域知识没有「一次性写完」的终点——随着真实 LLM 实测（L13）暴露问题、新的问题类型被识别、不同模型（Ollama / DeepSeek / Qwen 等）对提示词敏感度不同，知识包需要**持续迭代**。这不是一次性交付，而是随项目演进的持续工作。
- **长期目标**：
  1. **迭代现有知识包**：根据真实 LLM 输出复盘，修正术语、补充边界 case、优化 prompt 措辞。
  2. **扩充新知识包**：逐步覆盖 布局（定式 / 开局）、官子、手筋、形势判断细则、让子局常识等（新增 `resources/skills/*.md` 并同步 `SkillRegistry` 命中规则）。
  3. **加入 few-shot**：给关键知识包补少量示例问答，提升小模型（本地 Ollama 7B 级）的稳定输出。
  4. **多模型适配**：针对不同 provider 的指令遵循能力，微调 system prompt 的约束强度与长度。
  5. **诚实性护栏**：持续校验知识包不诱导 LLM 编造坐标 / 目数，守住 Grounding 契约。
- **产出**：`resources/skills/*.md` 的持续更新 + 实测记录（可在 `docs/` 下维护一份 skills 迭代日志）。
- **依赖**：真实 LLM 接入（L13）。

#### L16 — LLM 网络层崩溃修复（Qt6Network `interfaceNameFromIndex` 空指针）✅（P1，已修复：LLM 走 WinHTTP 直连，真机整盘对弈验证通过）
- **现象**：对局中**纯下棋、不讲话也会闪退**。崩溃点落在 `Qt6Networkd.dll` 的 `QNetworkInterface::interfaceNameFromIndex`，`mov (%rax),%rax` 且 `rax=8` 的空指针解引用（0xC0000005 访问违例；Event Viewer 另记录到一次 `0xC0000409` 栈缓冲区溢出，为同源内存破坏在不同构建下的另一表现）。
- **根因（精确定位）**：崩溃点 `QNetworkInterfaceManager::interfaceNameFromIndex` 只在枚举网卡时被调用（`addressFromSockaddr` 解析 IPv6 作用域 ID）。Qt6 的 `QNetworkAccessManager` 每次连 socket 都会经 `QHttpNetworkConnectionChannel` 启动 **QNetworkConnectionMonitor**（网络可达性监视器，`isEnabled()` 恒为 true、无公开 API 关闭），其 `setTargets → getInterfaceFromHostAddress → QNetworkInterface::allInterfaces()` 在 VPN / Hyper-V / VMware 虚拟网卡环境下空指针崩溃；且 `allInterfaces()` 无缓存、每次必重新枚举，故无法靠「预热」规避。D5.2「投机预生成」每手发请求放大了触发频率（「不讲话也崩」），但**主动提问同样会触发**。
- **临时缓解（已提交）**：`MainWindow::createAiServices` 将 `advisor_->setSpeculativeExplain(usingHttp)` 改为 `setSpeculativeExplain(false)`——对局中不再自动发请求，仅用户主动提问才发。形势判断 / KataGo / 复盘不受影响。
- **修复方案（已实现）**：
  1. **LLM 改走 WinHTTP 直连（根因修复）**：新增 `src/ai/conversation_http/winhttp_transport.{h,cpp}`（WinHTTP 同步 POST：http/https、超时、`WINHTTP_ACCESS_TYPE_NO_PROXY` 直连不查系统代理）；`HttpConversationService::doChat` 改为在后台线程调用 `winHttpPost` 并经 queued 回主线程处理，**完全绕开 Qt6Network 的 QNAM / QNetworkConnectionMonitor**，从源头消除崩溃。`answerStream`（SSE 流式）本项目未使用，改由基类 `answer` 兜底（非流式）；
  2. **恢复投机预生成**：`MainWindow` 将 `setSpeculativeExplain(false)` 改回 `setSpeculativeExplain(usingHttp)`，恢复 D5.2 原设计（未配置 LLM 时 `usingHttp=false` 仍不开启）；
  3. **测试**：`tests/test_http_tools.cpp` 新增 `http_service_constructs_available_and_direct`；另以本地 HTTP 服务冒烟验证 `winHttpPost` 与 `answer()` 端到端（POST + 解析 + 线程回调）通过；
  4. **升级 Qt（方向 3，保留）**：WinHTTP 已绕开问题路径；若日后仍需用 QNAM（如 HTTP/2 或系统代理场景），升级 Qt 规避该崩溃点。
- **后续优化手段**（功能已可用，以下为非阻塞优化）：
  1. **恢复 SSE 流式**：当前 `answerStream` 退化为非流式（本项目未使用）。若将来要「逐字流式呈现」讲解，可在 `winhttp_transport` 补 `WinHttpReadData` 增量回调 + SSE 解析，再恢复 `answerStream`；
  2. **系统代理 / HTTP/2**：WinHTTP 直连不支持系统代理与 HTTP/2；企业代理等场景需待 Qt 升级修复后回退 QNAM，或另接 libcurl；
  3. **连接复用**：当前每次请求新建 WinHTTP 会话，可缓存 `WinHttpOpen` 会话句柄以降低握手开销。
- **影响范围**：仅 LLM 对话路径；KataGo / 形势判断 / 复盘 / 摆棋均不受影响。
