## 2. 分项说明

### 2.1 引擎强度与真实性

#### L1 — 19 级难度真实 KataGo 标定 🧪
- **现状**：`strengthForLevel(1..19)` 映射已实现；`tools/calibrate_strength.cpp` 用离线引擎做过相邻档对弈 spike（单调递增已初步验证）。但「职业段 = 标准模型 + visits」的强度锚点未与真实 KataGo 对拍。
- **目标**：在装有 KataGo 的环境中，让相邻档位互相对弈（或与 KataGo 内置段位 / 公开等级分对标），校到「强度单调递增、相邻档有可感知差距」。
- **产出**：固化的最终映射表（更新 `ai/strength.cpp` 与 `docs/archive/技术路线-选型与任务计划.md` §2.2）。
- **阻塞解除条件**：需真实 KataGo + 标准 / HumanSL 模型（依赖 L13）。

#### L2 — 更细的难度标定 ⬜（P2）
- **现状**：19 级为初值映射，职业偶数段等细节靠 search-blend 插值，插值后的真实强度未标定；**新手（`rank_20k`）与业余1段（`rank_1d`）之间隔着约 20 个棋力等级，粒度严重不均**。
- **目标**：在 L1 基础上细化档位、校验 search-blend 插值效果；**补足新手带 `rank_15k/10k/7k/5k/3k/1k` 中间档**，使每一档都有可感知差距（与 D3.4 的「新手难度动态爬坡」共用同一阶梯，见设计文档 §5.5）。新手带阶梯已落地于 `strength.h` 的 `humanProfileForStrength`（D3.4），其 `rank_*` 档位待 L13 实测确认。

### 2.4 LLM 与交流质量

#### L9 — LLM 半提示完整实现 🧪（P1）
- **现状**：`req.hint` 已有模板方向提示 + HTTP 不泄露坐标；与真实 LLM 的「只给方向、不给坐标」联调未完整验证。
- **目标**：接入真实 LLM 后验证半提示在各类问题（死活 / 落点 / 形势）下都能只给方向。

#### L10 — 持续优化 LLM 模型的 Skills 🔁（P0，本次新增）
- **进展（D4）**：Skills 2.0 已落地——`Skill` 升级为 YAML frontmatter（id/name/description/applies_to/version/last_score）+ body；新增 TF-IDF 语义检索（`SkillRegistry::retrieve` 带命中理由，embedding 为后续前端）；`HttpConversationService` 经 `SkillRegistry::select`（类别白名单 + 检索 top-k、按 id 去重、受预算裁剪）注入。**D4.5 评估闭环已落地**：`skill_eval.*` 定义 golden Q&A 集 + `SkillEvalReport`（分类命中率 / Top-1 检索命中率 / 每技能评分 / 注入数 token 代理），纳入 CTest 作 release gate（`test_skill_eval`，命中率 ≥ 90% 才通过）。`version` + `last_score` 使 L10 从此有度量与完成标准。
- **背景**：通用 LLM 对围棋专业度不足，项目用 `resources/skills/*.md`（counting / ko / life-death / move-quality / terms 五个知识包）按问题类型注入 system prompt。这些知识包的质量直接决定 LLM 讲解的专业度与可信度。
- **为什么是长期任务**：围棋领域知识没有「一次性写完」的终点——随着真实 LLM 实测（L13）暴露问题、新的问题类型被识别、不同模型（Ollama / DeepSeek / Qwen 等）对提示词敏感度不同，知识包需要**持续迭代**。这不是一次性交付，而是随项目演进的持续工作。
- **长期目标**：
  1. **迭代现有知识包**：根据真实 LLM 输出复盘，修正术语、补充边界 case、优化 prompt 措辞。
  2. **扩充新知识包**：逐步覆盖 布局（定式 / 开局）、官子、手筋、形势判断细则、让子局常识等（新增 `resources/skills/*.md` 并同步 `SkillRegistry` 命中规则）。
  3. **加入 few-shot**：给关键知识包补少量示例问答，提升小模型（本地 Ollama 7B 级）的稳定输出。
  4. **多模型适配**：针对不同 provider 的指令遵循能力，微调 system prompt 的约束强度与长度。
  5. **诚实性护栏**：持续校验知识包不诱导 LLM 编造坐标 / 目数，守住 Grounding 契约。
- **产出**：`resources/skills/*.md` 的持续更新 + 实测记录（可在 `docs/` 下维护一份 skills 迭代日志）。
- **依赖**：真实 LLM 接入（L13）。

#### L11 — Grounding 校验器（输出 vs facts 回退）🧪（P0，由 D2 升格为一等门禁）
- **现状**：D2「Verify-then-Speak」已落地：`src/ai/verify/` 的 `ClaimExtractor`（`<claims>` JSON + 正文兜底）与 `ClaimVerifier`（目数 ±1.0 / 胜率 ±5pp / 坐标合法）对照 `GroundedFacts` 逐条校验，三档处置（通过 / 小偏差改写为引擎真值并标注 / 不可验证置 `unsure` 灰显）已接入 `AiAdvisor::deliverAnswer`；单测通过。**D2.4 证据溯源已落地**：校验后的断言带 `source` 挂到 `ConversationReply.verdicts`，聊天面板逐条 hover 看来源、点击高亮引擎主变化（跳 PV）；**D5.6 可观测已落地**：每次问答落一条 `agent_trace.jsonl`（position hash / route / model / latency / verify），本地「查看运行 trace」面板可查。待与真实 LLM 输出对拍（依赖 L13）。
- **目标**：真实环境验证幻觉句未拦截率 < 1%，坏样本回收进 telemetry 反哺评估闭环（D2.5）。

#### L12 — CommentaryPolicy（话痨 / 成本控制）⬜（P2）

- **目标**：只对关键手 / 大失误 / 提问讲解，控制 LLM 调用成本与话痨。

#### L16 — LLM 网络层崩溃修复（Qt6Network `interfaceNameFromIndex` 空指针）🧪（P1，已实现，待真实坏环境实测）
- **现象**：对局中**纯下棋、不讲话也会闪退**。崩溃点落在 `Qt6Networkd.dll` 的 `QNetworkInterface::interfaceNameFromIndex`，`mov (%rax),%rax` 且 `rax=8` 的空指针解引用（0xC0000005 访问违例；Event Viewer 另记录到一次 `0xC0000409` 栈缓冲区溢出，为同源内存破坏在不同构建下的另一表现）。
- **根因**：D5.2「投机预生成」（`AiAdvisor::prewarmExplanation`）在**每手 AI 落子后**后台自动发一条 HTTP 请求预生成「为什么下这里」；请求经 `QNetworkAccessManager` → Qt 内部枚举本机网卡 → 在部分 Windows 网络环境（疑似 VPN / Hyper-V / VMware 虚拟网卡 / 特定适配器）下 `interfaceNameFromIndex` 解引用空指针崩溃。因每手都发，故「不讲话也崩」。
- **临时缓解（已提交）**：`MainWindow::createAiServices` 将 `advisor_->setSpeculativeExplain(usingHttp)` 改为 `setSpeculativeExplain(false)`——对局中不再自动发请求，仅用户主动提问才发。形势判断 / KataGo / 复盘不受影响。
- **修复方案（已实现）**：
  1. **网络兜底（方向 1）**：新增 `src/ai/conversation_http/network_probe.{h,cpp}`，在主线程用 SEH（`__try/__except`）同步强制 Qt 完成一次网卡枚举 + 每个索引的名称映射解析（覆盖 `allInterfaces` / `interfaceNameFromIndex` 两条崩溃路径）；`HttpConversationService` 构造时调用 `networkInterfaceSafe()`，坏环境触发原生访问违例即置 `available_=false`，调用方自动降级到 `TemplateConversation`，保证 LLM 不可用时仍可用；
  2. **恢复投机预生成**：`MainWindow` 将 `setSpeculativeExplain(false)` 改回 `setSpeculativeExplain(usingHttp)`——坏环境因 `usingHttp=false` 不开启投机预生成，好环境恢复 D5.2 原设计；
  3. **验证残留（方向 4）**：坏环境的自检闸门覆盖「主动提问」与「投机预生成」两条路径（二者都经 `HttpConversationService` 构造）；真机坏环境（VPN / 虚拟网卡）无法在本机复现，需在有问题的网络环境实测确认拦截效果；
  4. **升级 Qt（方向 3，保留）**：若仍有残留（QNAM 工作线程的特定索引路径），升级 Qt 为根治手段。
- **影响范围**：仅 LLM 对话路径；KataGo / 形势判断 / 复盘 / 摆棋均不受影响。
